# Adaptive Security Agent: System Research Report

**Project:** Adaptive Security Agent (ARES prototype)  
**Report type:** System description, methodology, prototype evaluation, limitations, and future work  
**Status:** Research prototype; all attack traffic and defensive outcomes are simulated

## Abstract

The Adaptive Security Agent is a local, defensive security-operations prototype. It generates
synthetic traffic, sends it to an in-process demonstration application, classifies event windows,
selects simulated defensive actions, and records the outcome for future adaptation. Its central
agent loop is:

> **Generate → Log → Detect → Analyze → Decide → Respond → Remember → Learn → Improve**

Adaptation is intentionally separated into three mechanisms: incident-pattern memory, response
preference updates, and periodic Random Forest retraining. The main dashboard also provides a
bounded **Testing Mode** to run selected synthetic scenarios automatically against the agent.
An optional reinforcement-learning experiment compares a DQN policy with a fixed-rule baseline
inside a separate synthetic Gymnasium environment.

The project demonstrates an end-to-end software architecture and learning workflow, not
production-grade detection. It opens no sockets, accepts no real targets, and performs no real
blocking. Its current results are generated by clean synthetic scenarios and simulated response
feedback; they should not be interpreted as evidence of real-world protection.

## 1. Objectives and scope

### Objectives

- Demonstrate a complete defensive agent workflow using generated security-event windows.
- Show how learned attack memory can shorten analysis of repeated patterns.
- Adapt response preferences from simulated outcomes without silently changing ML weights.
- Provide an explicit, inspectable retraining step for the Random Forest detector.
- Make dashboard settings and test scenarios configurable without changing the model's core logic.
- Keep experimentation local, bounded, and safe to run as a software demonstration.

### Scope and non-goals

The current system is a self-contained simulation. It does **not** ingest real network traffic,
scan or exploit hosts, make external connections, enforce firewall rules, or use live analyst
feedback. The word “attacker” in Testing Mode describes generated scenario traffic, not a
standalone offensive tool.

The primary decision pipeline is rule/statistics based around a Random Forest classifier. It is
not an LLM-based reasoning system. The optional DQN is an experimental component and is not the
policy used by the dashboard's main agent loop.

## 2. System overview

| Component | Purpose |
|---|---|
| Streamlit dashboard (`app.py`) | SOC-style KPIs, event replay, Testing Mode, adaptation analytics, history, and settings |
| Synthetic simulator (`agent/simulator.py`) | Generates event dictionaries and processes them in a local demo application |
| Event validation (`agent/event_schema.py`) | Validates generated events, including RFC 5737 documentation-range source IPs |
| Feature extraction (`agent/features.py`) | Converts a batch into classifier and pattern-fingerprint features |
| Detector (`agent/detector.py`) | Random Forest prediction, confidence gate, novelty-distance check, and rule-baseline output |
| Analyzer (`agent/analyzer.py`) | Compares event fingerprints with memory, scores risk, and selects analysis depth |
| Planner (`agent/planner.py`) | Selects a response from a scenario playbook, adjusted by prior action outcomes |
| Simulated responder (`agent/responder.py`) | Records a local simulated response and produces synthetic success feedback |
| Memory (`agent/memory.py`) | SQLite incidents, patterns, action statistics, simulated defenses, and model-retraining history |
| Learner (`agent/learner.py`) | Reinforces patterns, updates response statistics, and prepares eligible model experiences |
| Testing Mode (`agent/testing_mode.py`) | Runs bounded scenario batches through the same sandbox and agent pipeline |
| RL experiment (`agent/rl_env.py`, `train_rl.py`) | Separate synthetic response-policy environment and DQN-vs-rule evaluation |
| Runtime settings (`agent/settings.py`, `config/settings.json`) | Validated thresholds, timing, replay defaults, and editable quick-launch presets |

### Safety boundaries

- Scenario traffic is generated in-process; the simulator does not open network sockets.
- Generated source addresses use documentation-only ranges (`192.0.2.x`, `198.51.100.x`,
  `203.0.113.x`).
- Demonstration credentials are fake and event logging removes the credential field.
- “Blocking,” rate limiting, MFA, and request rejection are represented by rows or outcomes in
  local SQLite state; they are not applied to real services.
- Testing Mode accepts only built-in scenario names, limits runs to 20 cases, and has no target
  address field.

## 3. Methodology

### 3.1 Synthetic scenario generation

The simulator creates event windows for scenarios such as normal traffic, brute-force login
attempts, port scans, SQL-injection-like payloads, DDoS-like traffic, suspicious logins, and
novel or unusual activity. Seeded generation can reproduce a window for tests. Replay controls
vary event count, intensity, structural modification, and random variation.

The baseline training-data builder creates labeled windows from the synthetic scenarios. The
scenario label is retained for dataset training and simulated feedback; it is not added as an
agent-visible event feature. In particular, event dictionaries and extracted feature vectors do
not include the ground-truth label.

### 3.2 Event processing and features

Generated events are validated, processed by the in-process demo application, and appended as
JSON lines to `data/security.log`. Detection reads the batch from that log and aggregates the
delivered events into a single window-level feature dictionary.

The classifier uses 11 features: destination port, protocol, packet rate, failed-login count,
request count, payload length, connection duration, unusual-port ratio, login frequency,
special-character ratio, and distinct-port count. A separate nine-feature normalized
fingerprint is used to compare events with remembered patterns. Rule-based thresholds are shown
alongside the model prediction as a baseline/explanation; the Random Forest remains the main
classifier.

### 3.3 Detection and novelty handling

The detector is a scikit-learn Random Forest classifier. The current default unknown gates are:

- maximum class probability below **0.65**, or
- normalized novelty distance above **3.0** from every class profile.

A model prediction of “Unknown Suspicious” also follows the unknown path. The second gate is
intended to reduce the risk of a forest assigning high confidence to an unfamiliar input.
Thresholds can be tuned in the dashboard or `config/settings.json`.

The detector also computes a risk score from scenario severity, confidence, and novelty. Risk
labels are LOW, MEDIUM, or HIGH. These are prototype scores and have not been calibrated against
real incidents or an operational risk standard.

### 3.4 Analysis paths and decisions

The analyzer converts the current event window into its normalized fingerprint, ranks stored
patterns by similarity, and compares the best match to the configurable memory-match threshold.
The default threshold is **0.90**.

| Path | Typical condition | Analysis depth |
|---|---|---:|
| `BASELINE` | Normal traffic | 2 steps |
| `FAST_MEMORY` | A sufficiently similar remembered pattern | 2 steps |
| `STANDARD` | A known model class with no matching memory pattern | 4 steps |
| `FULL_ANALYSIS` | Suspicious/unknown behavior without a matching pattern | 6 steps |

The planner starts from a scenario-specific response playbook. It uses smoothed success rates
from SQLite action statistics to prefer responses that have worked more often in the simulator.
The responder records the chosen action and obtains an outcome from a hidden simulated
effectiveness table.

### 3.5 Three distinct adaptation mechanisms

1. **Memory adaptation:** a new pattern fingerprint is stored; repeats reinforce its count,
   confidence, and centroid. This can make a repeat recognizable even when the classifier has
   not learned that pattern. It does not update model weights.
2. **Rule adaptation:** per-scenario action success statistics influence later planner choices.
   This does not update model weights.
3. **Model retraining:** the Random Forest is refit on the original synthetic dataset plus
   eligible labeled experiences from SQLite. Experiences are augmented with feature jitter.
   Retraining is available manually or after a configurable number of pending experiences; novel
   families require at least two sightings to become eligible. Only this operation changes model
   weights.

The displayed experience accuracy before/after retraining is **in-sample** on examples included
in training. It measures fit to stored experiences, not generalization. The separate holdout
score is from the original synthetic dataset split.

### 3.6 Testing Mode procedure

Testing Mode is an automated, bounded simulation of scenarios against the existing agent:

1. The user selects built-in synthetic scenarios, 1–5 rounds, and 5–40 events per scenario.
2. The UI limits each campaign to at most 20 scenario cases.
3. Each case gets generated events and a documentation-range source IP.
4. The in-process demo app writes those events to the sandbox log.
5. The same detector, analyzer, planner, responder, memory, and learner pipeline used by the
   Demo Attack Lab processes the batch.
6. Results show the generated scenario, model/agent classification, risk, response, simulated
   response success, and simulated containment. Normal traffic is not counted as a threat
   containment case.

The outcome is not a real intrusion-prevention measurement: it is determined by the simulator's
response feedback. A campaign may also update persistent pattern/action memory and may trigger
the configured retraining threshold.

### 3.7 Optional reinforcement-learning experiment

The separate Gymnasium environment models one synthetic scenario per episode. Its seven-value
observation consists of normalized packet rate, failed logins, requests, distinct ports, unusual
port ratio, login frequency, and remaining threat. Scenario labels are excluded from observations
and used only for simulator reward/outcome calculation.

The DQN action space is monitor, alert, simulated rate limit, simulated temporary block, and human
review. The reward function favors verified containment but applies costs for responses and
availability disruption; false blocking of benign activity has a larger penalty than a
successful threat containment reward. Training and evaluation write a model checkpoint, episode
CSV, and JSON metrics. The experiment is separate from the main dashboard response policy.

## 4. Prototype results and success cases

### 4.1 Functional success cases

The repository's headless end-to-end smoke run exercised the full agent loop and showed these
prototype behaviors:

- **First brute-force window:** classified as Brute Force at 99% displayed confidence, selected
  simulated `BLOCK_IP`, and created a new memory pattern.
- **Repeated brute-force window:** recognized through `FAST_MEMORY` and reinforced the stored
  pattern.
- **Novel behavior:** initially took `FULL_ANALYSIS` and a cautious `MONITOR_AND_LEARN` response;
  repeated similar windows were recognized from memory as a learned `Novel-*` family.
- **Previously blocked source:** a subsequent batch using the same simulated source was rejected
  by the demo application's local blocklist.
- **Normal traffic:** followed the baseline path and selected `ALLOW`.
- **Model retraining:** a smoke run reported 1.00 holdout accuracy on the clean synthetic split;
  experience accuracy increased from 0.769 to 1.00 on the training experiences. The latter is
  explicitly in-sample, and neither number estimates real-world accuracy.

These are functional demonstrations from synthetic scenarios, not independent security
benchmarks. The simulated response success rate is generated from the responder's effectiveness
table and should not be read as a real containment rate.

### 4.2 Automated test coverage

The test suite covers event-schema restrictions, reproducible generation, feature/rule behavior,
runtime-setting validation, threshold overrides, Testing Mode plan bounds and a local campaign,
passive API validation/authentication/idempotency/recommendation behavior, and the RL
environment/training/evaluation interfaces. The current suite passes **27 unit tests**. The API
endpoint persistence path is tested with a mocked session; an actual PostgreSQL/container
deployment was not run in this environment.

Passing these tests verifies implemented interfaces and selected expected behaviors; it does not
establish detection quality on real or independently collected traffic.

### 4.3 Saved DQN smoke evaluation

The checked-in evaluation output records a short smoke experiment: **256 training timesteps**,
**4 deterministic held-out episodes**, seed 7, and held-out seeds 100007–100010. The sample
contains one benign unusual-activity episode and three threat episodes (two DDoS and one port
scan).

| Metric | DQN | Fixed-rule baseline |
|---|---:|---:|
| Mean reward across four episodes | -0.60 | -2.49 |
| Threat containment | 0/3 (0%) | 3/3 (100%) |
| False-positive actions | 8 | 0 |
| Observed action choices | Alert only | Monitor, simulated rate limit, human review |

This tiny smoke evaluation is not statistically meaningful and is not a final policy comparison.
It exposes an important prototype issue: the DQN's mean reward was higher in this sample despite
zero containment because the reward structure also rewards alerting and penalizes actions. Reward
and evaluation metrics must therefore be reviewed together; reward alone is not a sufficient
security objective.

## 5. Limitations and threats to validity

### Data and generalization

- Training and tests use synthetic, deliberately structured scenarios. The data is much cleaner
  and more separable than real network telemetry; near-perfect synthetic holdout accuracy is
  expected and does not transfer to production traffic.
- Scenario coverage, class balance, noise, temporal drift, and attack/benign overlap are limited.
- The fixed set of manually engineered features and similarity dimensions may miss important
  behaviors or encode simulator-specific patterns.
- No evaluation has been reported on a real, independently collected, privacy-reviewed dataset.

### Labels and evaluation

- The simulator supplies ground truth to training and outcome feedback. Production labels would
  be delayed, incomplete, disputed, or based on analyst review.
- The responder's hidden effectiveness table creates simulated outcomes; it does not observe
  whether a real defense worked.
- “Containment,” confidence, risk, and success metrics are prototype concepts and are not
  calibrated operational service-level measurements.
- In-sample retraining experience accuracy is optimistic by construction. Novel labels are
  assigned by the agent and only become eligible after repeat sightings; this is not independent
  analyst confirmation.
- The four-episode DQN smoke evaluation is too small to support comparisons or claims of policy
  quality. Its zero containment result for the trained policy should motivate more training and
  reward validation, not be hidden by its higher sample mean reward.

### Architecture and operations

- SQLite is a local, single-node memory store; there is no multi-user isolation, distributed
  coordination, or demonstrated concurrent-write strategy.
- There is no production telemetry adapter or event-streaming service. The new API accepts
  caller-supplied aggregate windows only; it has no configured retention/expiry policy,
  fine-grained RBAC, production audit pipeline, or incident-response integration.
- There is no production deployment mechanism for ML model versioning, rollback, shadow testing,
  or drift monitoring.
- Runtime thresholds are user-tunable, but changes can alter unknown classification and memory
  matching. The dashboard does not establish an optimal setting for any real environment.
- A scikit-learn version warning occurred during a local smoke run because the persisted detector
  artifact was created with a different library version than the runtime. Reproducible model
  loading requires artifact/dependency version management.
- The dashboard is designed as a local demonstrator; authentication, authorization, hardening,
  and multi-tenant controls are not provided.
- The passive API adds tenant-scoped bearer-key authentication and tenant-scoped persistence,
  but has no self-service client lifecycle, role model, per-tenant rate quota, automated
  retention, or remote deployment validation yet.

## 6. Future work

### Website integration foundation (passive API)

The project now includes an initial, separately deployable passive scoring API (`api/`) and a
Docker Compose PostgreSQL pilot. An authorized website **backend** can send pre-aggregated,
strictly validated feature windows over `POST /v1/windows/score`. Requests require a
tenant-scoped bearer API key and a client-generated UUID event ID. The API stores scores in a
tenant-scoped PostgreSQL table with a uniqueness constraint for retry-safe idempotency. It
returns the existing detector's classification and a recommendation from the existing response
playbook; the API does not execute the recommendation, store raw IP addresses, or accept raw
traffic, credentials, or target addresses. Health/liveness routes, a readiness check, bounded
request bodies, versioned schema migrations, and a non-root container are included.

This is an integration foundation, **not a production certification**. The first release is
passive and deliberately does not connect website scoring to the Streamlit app's SQLite memory,
simulated action-outcome learner, retraining workflow, or live enforcement. The recommendation
uses the existing playbook without API-side outcome history. The caller must be a trusted
server-side integration; API keys must never be embedded in browser code. Remote deployment
still requires TLS, restricted ingress, reverse-proxy rate limiting, secret management and
rotation, PostgreSQL backup/retention operations, monitoring, and an independently validated
model and event mapping.

### Near-term research improvements

1. **Reproducible evaluation:** publish fixed seeds, dataset-generation parameters, per-class
   confusion matrices, precision/recall/F1, false-positive rates, calibration metrics, and
   confidence intervals across multiple runs.
2. **Harder synthetic data:** add benign/attack overlap, missing and noisy events, changing
   baselines, variable time windows, class imbalance, and unseen scenario families.
3. **Holdout discipline:** reserve scenario variants and time periods for tests; avoid reporting
   training experience accuracy as model improvement. Add a separate, never-trained-on evaluation
   set for novel patterns.
4. **DQN objective revision:** tune rewards against explicit security objectives, assess
   containment and false positives independently, increase training and held-out episode counts,
   compare several seeds, and retain the fixed-rule baseline.
5. **Threshold studies:** sweep confidence, novelty, and memory-similarity thresholds and report
   the trade-off between false positives and missed detections rather than selecting values from
   demo behavior alone.
6. **Model artifact reproducibility:** record library versions, dataset/version identifiers,
   model metadata, and training configuration; add safe compatibility checks and explicit
   retraining instructions.

### Longer-term engineering work

- Add opt-in ingestion adapters for sources such as Zeek, Suricata, or syslog, initially in
  offline/replay mode and with explicit data minimization.
- Introduce analyst review/feedback workflows with provenance, correction history, and label
  confidence before feedback can be used for retraining.
- Add drift monitoring, model registry/versioning, shadow evaluation, canary rollout, and
  rollback before any model update is operationalized.
- Explore calibrated open-set detection or anomaly models alongside the existing Random Forest;
  benchmark rather than assume that a more complex model is better.
- Improve pattern retrieval as memory grows, with indexed/vector search and per-tenant isolation
  only if validated requirements call for them.
- Treat any future real enforcement as a separate, opt-in integration requiring authorization,
  approval gates, least privilege, audit logs, rate limits, and tested rollback.
- Add production controls such as authentication, RBAC, secrets management, privacy/retention
  policies, observability, CI, and dependency/security update processes.
- Consider guarded LLM-generated incident summaries only as a presentation aid; keep
  enforcement decisions within explicit, testable policy controls and require human review where
  appropriate.

## 7. Reproducibility and operation

From the project directory, create/activate the virtual environment and install `requirements.txt`
as described in `README.md`. Run:

```powershell
python train.py
python -m unittest discover -s tests -v
python smoke_test.py
python train_rl.py --smoke
python -m streamlit run app.py
```

`train_rl.py --smoke` is a short interface/training check, not a performance benchmark. Full RL
training and held-out evaluation accept explicit timestep, episode-count, and seed arguments; save
those settings with any reported result.

## 8. Conclusion

The Adaptive Security Agent demonstrates how synthetic event generation, supervised detection,
novelty checks, pattern memory, outcome-based response preferences, explicit model retraining,
and an inspectable dashboard can be integrated into one defensive workflow. Testing Mode makes
that workflow repeatable for bounded scenario campaigns while preserving its local-only safety
boundary.

The most important research conclusion is also the primary caveat: successful end-to-end
simulation is not equivalent to demonstrated real-world security efficacy. The next meaningful
step is stronger, reproducible, independently held-out evaluation—not connecting the current
prototype directly to production enforcement.
